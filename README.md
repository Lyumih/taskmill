# Taskmill

Taskmill — инструмент для организации работы над задачами в проекте. Он помогает сохранять проектный контекст и проходить подходящий workflow для разных типов задач. Инструмент рассчитан на индивидуальных разработчиков и команды.

## Ссылки

- [Веб-версия](https://taskmill-web.vercel.app/)
- [Репозиторий на GitHub](https://github.com/Lyumih/taskmill)

## Как это работает

1. Скилл или агент изучает проект и создаёт JSON-конфигурацию и файлы задач в `.taskmill/`.
2. Пользователь подключает папку `.taskmill` в веб-интерфейсе через системный выбор папки браузера.
3. Веб-интерфейс проверяет JSON по схемам Taskmill, показывает проект и сохраняет изменения обратно в выбранную папку.

Данные проекта хранятся в `<project>/.taskmill/`: `config.json`, `tasks/*.json` и `.trash/`. В браузере нужно выбрать именно папку `.taskmill`, а не весь репозиторий. File System Access API требует разрешения пользователя и доступен не во всех браузерах. CLI, MCP и локальный сервер остаются возможными дополнительными интерфейсами к тем же файлам.

## Формат файлов

- `schemas/taskmill-config.schema.json` — схема конфигурации проекта (`schemaVersion: 1`, project identity, process overrides и необязательные plugin overrides).
- `schemas/taskmill-task.schema.json` — схема файла задачи (`schemaVersion: 1` и нормализованный `TaskData`).
- `schemas/taskmill-config.example.json` и `schemas/taskmill-task.example.json` — проверяемые примеры конфигурации и задачи.
- Задача хранится как `.taskmill/tasks/<taskId>.json`; `task.id` должен совпадать с именем файла без расширения.
- Схемы являются версионируемым контрактом. При несовместимых изменениях нужно добавить новую версию схемы и явную миграцию.
- Базовые процессы (`feature`, `bugfix`, `support`, `review`) поставляются Taskmill. Если `processes` в конфиге отсутствует или пуст, используются шаблоны по умолчанию. Проект может задать частичные overrides по `id`; незаданные поля наследуются, а `stages` и `blocks` при явном задании заменяются целиком. Задача может аналогично задать `task.processOverride`; приоритет: template → project → task.
- Поле `$schema` допускается в обоих форматах. После выпуска схемы его можно направить на файл из immutable Git-тега; не используйте изменяемый `main` как версию контракта.

Для старта скопируйте `schemas/taskmill-config.example.json` в `<project>/.taskmill/config.json` и замените ID и имя проекта. Процессы по умолчанию подключатся без дополнительных записей. Чтобы переопределить процесс, добавьте в `processes` объект с его `id` и только нужными полями. Запустите локальный web-клиент (`npm start`) и выберите `<project>/.taskmill`. После перезагрузки браузера папку потребуется выбрать повторно; дескриптор пока не сохраняется между сессиями.

## Модель workspace

- Плагин-блок — переиспользуемая реализация и схема содержимого в `apps/web/src/plugins/<plugin-id>`. Общие редакторы полей находятся в `apps/web/src/components`.
- Проект хранит доступность и значения плагинов, а также список процессов.
- Процесс задаёт тип задачи, этапы и упорядоченные ссылки на экземпляры плагинов.
- Задача хранит `processId`, переопределения значений и заметки отдельно для каждого процесса, экземпляра блока и поля; пока переопределения нет, используется значение проекта. Непустые заметки входят в копируемый контекст задачи.
- Task-блоки из legacy mock fixtures переносятся в `pluginData` при загрузке реестра; рабочий тип `TaskData` содержит plugin values, а не дублирует их отдельными секциями.
- Страница задачи позволяет выбрать процесс и заполнить его активные блоки; страницы блоков и процессов редактируют те же данные проекта.
- Демо-проекты по-прежнему загружаются из mock registry и хранят изменения только в памяти.
- Подключённый `.taskmill` workspace загружается из выбранных JSON-файлов и сохраняет изменения в них; внешние изменения можно перечитать кнопкой «Обновить».

## Направление развития

- Поддерживать разные workflow для новых возможностей, исправлений, исследований и других типов задач.
- Уточнять вопросы и шаги workflow по итогам выполнения задач.
- Сохранять описание проекта в переносимом, структурированном виде, который может читать локальный сервер.

## Технологии

- Веб-клиент: React, Ant Design, TanStack Query.
- Управление пакетами и приложениями: npm Workspaces.
- Файловое подключение web-клиента использует JSON Schema и File System Access API; локальный сервер не требуется для базового персонального сценария.

## Первый этап

Поддерживать версионируемые JSON-схемы проекта и задач. Skills создают эти файлы, браузерный клиент подключает выбранную папку и сохраняет изменения локально. Сервер можно добавить позже для браузеров без File System Access API, автоматического обнаружения изменений или интеграции с другими клиентами.
