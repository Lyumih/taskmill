# Инициализация задачи Taskmill

Начни работу над задачей и создай отдельный TypeScript-файл задачи, совместимый с данными Taskmill dashboard. Контекст и план решения хранятся вместе в объекте `TaskData`; отдельный Markdown-файл плана не создавай.

## Входные данные

Принимай путь к существующему файлу задачи, название или ID проекта и любое количество ссылок на источники. Файл задачи и другие исходные материалы разрешено только читать; не изменяй их. Источниками также могут быть локальные файлы и каталоги, ключи или URL Jira, URL или ID MR GitLab, имена веток и другие явно указанные ссылки.

Примеры:

- `taskmill-init tasks/0001/task0001.md проект cross` с уточнением «два игрока на одном устройстве» — прочитать задачу и создать `apps/web/mock/cross/0001.ts` с экспортом `taskMock: TaskData`, включив подтверждённый режим в описание и план.
- `taskmill-init tasks/0002/task0002.md APP-124 feature/new-search docs/requirements.md` — собрать контекст из источников и сформировать TaskData; если проект или ID задачи неоднозначны, сначала уточнить их у пользователя.

Если задача или проект не указаны либо не могут быть однозначно определены по запросу и доступным источникам, спроси пользователя в чате. Не выбирай проект только по текущей рабочей директории, если есть несколько правдоподобных вариантов. Для существующего проекта бери ID из dashboard registry. Для нового проекта сохраняй указанное имя в `project.name`; используй явно указанный ID, а если дана только простая однозначная метка вроде `cross`, используй её также как `projectId`. Неоднозначное имя не преобразуй в ID без уточнения. Не добавляй новый проект в registry автоматически.

## Выходной файл TaskData

Создавай файл по схеме `apps/web/mock/<projectId>/<taskId>.ts` относительно корня Taskmill dashboard. Определи dashboard root как корень, содержащий `apps/web/src/types/task.ts` и `apps/web/mock/index.ts`; если его нельзя однозначно найти среди workspace/настроек, спроси путь у пользователя. Экспортируй объект с именем `taskMock` и типом `TaskData`, используя импорт `../../src/types/task` для этой структуры каталогов. Перед записью проверь актуальный тип и mock-файл того же проекта; если проект новый и соседних файлов нет, используй `apps/web/mock/example/0001.ts` как образец формата. Следуй контракту, но не копируй нерелевантные демонстрационные значения.

В объекте `TaskData` заполняй подтверждённые поля задачи. План включай в поле `plan` как `summary` и упорядоченные `steps`; при наличии полезной конкретики используй `actions`, `expectedResult` и `verification`. Для нового плана ставь `progress: 0`, а невыполненным шагам — `status: 'pending'`. Не создавай отдельный Markdown-план с дублирующим содержимым.

По тем же шагам плана заполняй `expectedComponents`: указывай диапазон ожидаемых файлов, уверенность и основание оценки, количество экземпляров конкретных UI-компонентов библиотеки, API-статус (`available`, `needsVerification` или `unavailable`) с источником проверки, а также список создаваемых кастомных компонентов. Для каждого компонента из библиотеки добавляй `documentationUrl` с прямой ссылкой на официальную страницу компонента, если её наличие и URL подтверждены; не придумывай ссылки. Для каждого кастомного компонента указывай роль и размещение: локально в модуле или в общей библиотеке, с обоснованием переиспользования. Не включай `Flex` в подсчёт. Предпочитай локальное размещение; рекомендуй общую библиотеку только при подтверждённом повторном использовании в нескольких независимых модулях. Если целевой репозиторий или версия библиотеки неизвестны, снижай уверенность и ставь `needsVerification`, а не утверждай, что API доступен.

Определяй `taskId` по явному ID задачи или однозначному ID в исходном пути/источнике. Если ID неизвестен, неоднозначен или уже занят в каталоге выбранного проекта, спроси пользователя; не придумывай и не переиспользуй ID.

Если каталог проекта отсутствует, его можно создать для нового mock-файла. Если целевой файл уже существует, прочитай его и не перезаписывай молча: спроси, обновить ли его или выбрать другой ID. Перед записью покажи пользователю путь, проект и ID, а также краткое описание создаваемых данных.

Файл задачи предназначен для последующего подключения к dashboard. Само наличие файла не добавляет его в интерфейс: `apps/web/mock/index.ts` использует явные импорты и список задач проекта. По умолчанию меняй только новый файл `TaskData`; не редактируй реестр, UI или код приложения. Если пользователь отдельно попросил сразу показать задачу в dashboard, зарегистрируй импорт и добавь задачу в список проекта в `apps/web/mock/index.ts`. Для нового проекта добавь запись проекта только после проверки обязательной структуры `MockProject`; неизвестные проектные данные не выдумывай, а уточни.

## Порядок работы

1. Прочитай файл задачи, относящиеся к нему инструкции проекта, `TaskData` и один mock-файл того же проекта; для нового проекта используй образец `apps/web/mock/example/0001.ts`. Не меняй исходную задачу.
2. Установи проект, dashboard root, `projectId` и `taskId` по явно указанным данным, registry и источникам. Если есть несколько возможных проектов/root-каталогов или ID, уточни их в чате.
3. Проверь доступные источники. Если источник недоступен, сообщи об этом; не утверждай, что проверил Jira, MR, ветку или локальный файл, если доступа не было.
4. До записи спроси о недостающих или противоречивых сведениях, которые влияют на проект, цель, объём или направление решения. Не подменяй ответы предположениями. Подтверждённые факты, ограничения и оставшиеся некритичные вопросы отрази в подходящих полях TaskData, например `references`, `workflow.questions` или `feedback.items`.
5. Составь краткий, применимый план в `plan.summary` и `plan.steps`. Формулируй проверяемые шаги и ожидаемые результаты; не выдумывай сроки, оценки, ответственных или результаты проверок.
6. Создай только TypeScript-файл `TaskData` в каталоге выбранного проекта. Не меняй исходный файл задачи. Не редактируй `apps/web/mock/index.ts`, UI и другие файлы, если пользователь явно не запросил подключение задачи к dashboard.
7. Сообщи путь к созданному файлу, подтверждённый проект и ID, проверенные/недоступные источники и оставшиеся вопросы. Укажи, что файл задачи-источника не изменялся и что новый mock ещё не зарегистрирован в dashboard, если реестр не менялся.

TypeScript mock-файл — формат входных демонстрационных данных текущего dashboard, а не утверждение о будущем постоянном формате хранения Taskmill. Не копируй учётные данные, токены и не относящиеся к делу персональные данные. Не вставляй большие diff целиком: сохрани ссылку или краткое описание изменений.
