# Инициализация задачи Taskmill

Начни работу над задачей и создай отдельный JSON-файл в хранилище `.taskmill` целевого проекта. Контекст и план хранятся вместе в объекте `TaskData` в поле `task`; отдельный Markdown-файл плана не создавай.

## Входные данные

Принимай путь к существующему файлу задачи, название или ID проекта и любое количество ссылок на источники. Файл задачи и другие исходные материалы разрешено только читать; не изменяй их. Источниками также могут быть локальные файлы и каталоги, ключи или URL Jira, URL или ID MR GitLab, имена веток, ссылки Confluence, Swagger UI/OpenAPI/Swagger-файлы и другие явно указанные ссылки.

Примеры:

- `taskmill-init tasks/0001/task0001.md` — прочитать задачу и создать `.taskmill/tasks/0001.json` в корне проекта, включив подтверждённый контекст и план.
- `taskmill-init tasks/0002/task0002.md APP-124 feature/new-search docs/requirements.md` — собрать контекст из источников и сформировать JSON `TaskData`; если корень проекта или ID задачи неоднозначны, сначала уточнить их у пользователя.
- `taskmill-init tasks/0003/task0003.md APP-125 docs/openapi.yaml` — проверить API-контракт по указанной Swagger/OpenAPI-спецификации и отразить только подтверждённые операции.

Определи корень целевого проекта по явному пути пользователя или ближайшему родительскому каталогу, содержащему `.taskmill/config.json`. Не используй корень репозитория Taskmill skills или dashboard как корень данных. Если конфиг не найден или проект нельзя определить однозначно, спроси пользователя; не создавай конфиг автоматически. Читай `project.id`, `project.name` и `processes` из `.taskmill/config.json`; не ищи проект в dashboard registry и не добавляй его туда.

## Определение процесса

До анализа блоков, составления плана и заполнения `TaskData` определи, к какому процессу относится задача. Источник истины — массив `processes` в `.taskmill/config.json` (`id`, `taskType`, `trigger`, `enabled`, `blocks`). Если определения отсутствуют или конфиг не соответствует схеме, уточни у пользователя; не подставляй dashboard defaults и не выдумывай процессы.

Сопоставь процесс с явным типом/категорией задачи и правилами `trigger`/`taskType` из конфигурации и источников. Учитывай Jira issue type, описание и acceptance criteria, команду пользователя и связанный MR как свидетельства; при конфликте отдавай приоритет явному указанию пользователя или типу задачи в authoritative source, а конфликт укажи и уточни, если он меняет процесс. Не выбирай процесс только по ключевым словам в summary или по имени ветки. Не переключайся на другой процесс только потому, что подходящий процесс помечен как placeholder или его этапы ещё не настроены.

Запиши подтверждённые `processId` и соответствующий `type` в `TaskData`. `processId` определяет набор отображаемых блоков: строй дальнейший анализ и заполняй `pluginData[processId][blockId]` только для блоков выбранного процесса. Не переноси автоматически все блоки из другого процесса. Если процесс нельзя определить однозначно или подходящего процесса нет, не назначай `feature` по умолчанию и не создавай файл до уточнения. Укажи основания выбора и незакрытую неопределённость пользователю.

## Выходной JSON-файл задачи

Создавай файл `.taskmill/tasks/<taskId>.json` относительно корня целевого проекта. Формат файла: `{ "schemaVersion": 1, "task": { ... } }`, где `task` соответствует нормализованному `TaskData`. Не создавай TypeScript-модули, не импортируй тип в JSON и не исполняй файлы проекта. JSON Schema для конфигурации и задачи хранится в `schemas/taskmill-config.schema.json` и `schemas/taskmill-task.schema.json` в исходниках Taskmill; следуй схеме задачи. Если JSON Schema недоступна, остановись и уточни, не выдумывай формат.

Заполняй основные поля `TaskData` (`id`, `title`, `type`, `processId`, `description`, `status`, `priority`, `project`) только подтверждёнными сведениями. Остальные данные записывай в `pluginData[processId][blockId]`: план — в блок процесса с `pluginId: agent-plan`, ожидаемые компоненты — `expected-components`, API-сценарии — `api-error-handling`, permissions/flags — `permissions-flags`, workflow — `task-workflow`, ссылки — `task-references`, изменения — `branch-changes`, оценки — `time-estimates`, агенты — `task-agents`, даты — `task-dates`, обратная связь — `task-feedback`. Находи соответствующий `blockId` в выбранном process definition и точные имена полей в актуальном plugin definition Taskmill; не выдумывай плагин, блок или поле. Если определения доступны не полностью, заполняй только подтверждённые core-поля и уточняй остальное. План составляй из упорядоченных проверяемых шагов; для новых шагов ставь `pending`. Не создавай отдельный Markdown-план.

Определяй `taskId` по явному ID задачи или однозначному ID в исходном пути/источнике. Если ID неизвестен, неоднозначен или уже занят в каталоге выбранного проекта, спроси пользователя; не придумывай и не переиспользуй ID.

Если `.taskmill/tasks/` отсутствует, его можно создать. Если целевой файл уже существует, прочитай его и не перезаписывай молча: спроси, обновить ли его или выбрать другой ID. Перед записью покажи пользователю путь, проект и ID, а также краткое описание создаваемых данных. Записывай только внутри `<project-root>/.taskmill/`.

До записи явно сообщи:

- корень проекта с `.taskmill/config.json` и целевую папку `.taskmill/tasks`;
- полный путь к JSON-файлу задачи и существует ли файл уже; если папки ещё нет, укажи, что она будет создана;
- путь к исходному файлу задачи и найденным `AGENTS.md`/инструкциям проекта, а также удалось ли их прочитать.

Данные задачи и все plugin values хранятся в том же JSON-файле; отдельный файл плана не создавай. Не создавай файл инструкций (`AGENTS.md` или другой) автоматически: если он отсутствует, сообщи об этом. Если пользователь отдельно просит новый файл инструкций, сначала уточни его путь и содержание; это отдельное изменение вне стандартного `taskmill-init`.

Файл в `.taskmill` является данными проекта и подхватывается Taskmill при подключении этой папки в интерфейсе. По умолчанию создавай только файл задачи; не редактируй config, UI, код приложения или Taskmill source tree.

## Порядок работы

1. Прочитай файл задачи, относящиеся к нему инструкции проекта, `.taskmill/config.json` и JSON Schema задачи из исходников Taskmill. Не меняй исходную задачу.
2. Установи корень проекта по явному пути или `.taskmill/config.json`, затем подтверди `projectId` и `taskId`. Если корень, проект или ID неоднозначны, уточни их в чате.
3. Определи процесс по правилам выше до выбора анализируемых блоков и подготовки плана. Зафиксируй `processId` и `type`; при неоднозначности сначала уточни.
4. Проверь доступные источники. Для Swagger/OpenAPI сопоставь планируемые `method` и `endpoint` с реально объявленными операциями и схемами; не вызывай API-операции. Если доступен только Swagger UI без читаемой спецификации, снизь уверенность и укажи, что контракт не удалось проверить. Если источник недоступен, сообщи об этом; не утверждай, что проверил Jira, MR, Swagger, ветку или локальный файл, если доступа не было.
5. До записи спроси о недостающих или противоречивых сведениях, которые влияют на проект, цель, объём, направление решения или выбор процесса. Не подменяй ответы предположениями. Подтверждённые факты, ограничения и оставшиеся некритичные вопросы отрази в core-полях или значениях активных plugin blocks.
6. Составь краткий, применимый план в полях plugin block `agent-plan`, согласованный с блоками выбранного процесса. Формулируй проверяемые шаги и ожидаемые результаты; не выдумывай сроки, оценки, ответственных или результаты проверок.
7. Создай только JSON-файл по пути `.taskmill/tasks/<taskId>.json`. Проверь его по Taskmill task schema и убедись, что путь записи находится внутри `.taskmill`. Не меняй исходный файл задачи, config или Taskmill source tree.
8. Сообщи корень проекта и путь к созданному файлу, подтверждённый проект, `processId` и `type`, основания выбора процесса, существование/статус файла инструкций, проверенные/недоступные источники и оставшиеся вопросы. Укажи, что файл задачи-источника не изменялся.

JSON-файл задачи в `.taskmill` — рабочая запись проекта. Не копируй учётные данные, токены и не относящиеся к делу персональные данные. Не вставляй большие diff целиком: сохрани ссылку или краткое описание изменений.
