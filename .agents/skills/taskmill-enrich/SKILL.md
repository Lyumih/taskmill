# Глубокий анализ задачи Taskmill

Прочитай подготовленную запись задачи, исследуй её источники и заполни относящиеся к выбранному процессу блоки. Все результаты сохраняй в `.taskmill/tasks/<taskId>.json`; не создавай отдельные файлы плана и не печатай большие значения блоков в чате.

## Предварительные условия

1. Найди корень проекта по явному пути или ближайшему `.taskmill/config.json`. Работай только с задачей `.taskmill/tasks/<taskId>.json` этого проекта.
2. Прочитай JSON, `schemas/taskmill-task.schema.json`, `config.json` и применимые инструкции проекта. Убедись, что `task.id` совпадает с именем файла.
3. Требуй `preparationStatus: "ready"` и подтверждённый существующий `processId`. Если подготовка ещё не подтверждена или процесс отсутствует, остановись и попроси завершить `taskmill-init` и проверить задачу в интерфейсе. Не запускай анализ по устаревшему контексту чата.
4. Совместимость: для задачи, созданной до появления lifecycle-полей, разрешено продолжить без `preparationStatus` и `fillStatus`, если `processId` указан и существует. Новые черновики `taskmill-init` всегда имеют `preparationStatus: "reviewRequired"`, поэтому это исключение их не разблокирует.
5. Если `fillStatus` равен `complete` и пользователь не просит повторный анализ, верни краткую сводку, что данные уже сохранены в файле, и не перечитывай источники. Для `stale` или `partial` анализируй актуальные источники при явном запуске этого skill.

## Определение процесса и области заполнения

- Возьми базовые process definitions из `apps/web/src/processes/defaults.ts` Taskmill source tree и примени overrides из `.taskmill/config.json` по `id`. Примени `task.processOverride`, если он есть. Отсутствующие поля наследуются; заданные `stages` и `blocks` заменяют массивы целиком.
- Убедись, что `task.type` согласуется с выбранным процессом. Если обнаружен конфликт с подтверждённым типом задачи или пользовательским указанием, остановись и уточни до анализа.
- Заполняй только включённые блоки выбранного итогового процесса. Найди точные `blockId`, `pluginId`, поля и допустимую структуру в определениях процесса и plugin definitions Taskmill. Не выдумывай блоки, поля или форматы и не переноси автоматически значения из других процессов.

## Анализ источников и заполнение

1. Используй `task.sources` и явно переданные пользователем дополнительные материалы. Повторно проверь актуальную доступность, затем изучай только относящееся к задаче содержимое. Доступ к системе или ссылка сами по себе не подтверждают содержание.
2. Для Jira загрузи skill `jira` и применяй подходящие read-only инструменты. Для Confluence используй поиск и чтение страниц; для GitLab — MR, diff, ветку и связанный issue при наличии. Локальные файлы и инструкции только читай. Для Swagger/OpenAPI сопоставляй планируемые `method`, `endpoint` и схемы с опубликованной спецификацией; не вызывай API и не генерируй клиентский код.
3. Различай подтверждённые факты, выводы и неизвестные сведения. При противоречиях приоритет имеют явное указание пользователя и authoritative source; влияющие на направление решения противоречия сначала уточни. Не выдумывай оценки, даты, владельцев, проверки или подтверждённые связи.
4. Заполняй только поля применимых блоков, используя формат plugin definitions. План записывай в блок `agent-plan` как краткие упорядоченные проверяемые шаги со статусом `pending`. Связанные источники копируй в блок `task-references`, если такой включённый блок есть. Для остальных данных используй только соответствующие реально объявленные блоки и поля.
5. Сохраняй уже существующие `pluginData`, `pluginNotes`, общие task fields и данные других процессов. Не очищай блоки другого процесса. Если результаты предыдущего анализа устарели, обнови только целевые блоки текущего процесса; при конфликте с явно ручными значениями уточни перед перезаписью.
6. Если часть анализа невозможна из-за недоступности источников, заполни подтверждённую часть и зафиксируй ограничения в подходящих полях. Установи `fillStatus: "partial"`, если существенные блоки остались неполными; иначе `fillStatus: "complete"`.
7. Перед записью кратко покажи файл и перечень затрагиваемых блоков, затем сохрани обновлённый JSON и проверь его по `schemas/taskmill-task.schema.json`. Не изменяй `preparationStatus`; при нормальном завершении сохраняй `ready`.

## Повторный запуск и итог

`fillStatus: "complete"` означает, что глубокий анализ уже выполнен и записан. Не запускай дорогой повтор автоматически. Если пользователь явно просит повтор, либо `fillStatus` равен `stale`/`partial`, перечитай актуальный файл и источники, обнови целевые блоки и статус. При ошибке записи не утверждай, что результаты сохранены; при невозможности записать файл не выставляй `complete`.

В ответе сообщи путь к JSON, итоговый статус (`complete`/`partial`), обработанные блоки, ключевые ограничения и оставшиеся вопросы. Содержимое блоков пользователь увидит из файла через Taskmill; не повторяй его в чате. Не изменяй исходную задачу, `.taskmill/config.json`, Taskmill source tree, Jira или GitLab.
